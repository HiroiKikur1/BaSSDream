# 文案

## 1. 文字是设计内容

- **文字只为让人看懂、会用而存在。** 写之前先问：这里不写会怎样？如果答案是"也能懂"，就不写。
- **按用户的说法命名。** 用户说"管理通知"，不要写成"webhook 配置"。
- **一个动作从头到尾一个名字。** 按钮写"发布"，结果提示就写"已发布"。
- **主动语态，动词开头，句子短。**

## 2. 产品姿态

- **先想清产品是什么角色。** 工具、助手、教练、伙伴，各自的说话方式不同。没有被要求当教练，就不要说教。
- **姿态放低。** 用户是懂行的人：
  - 不解释显而易见的东西；
  - 不放"小提示""你可以……"；
  - 不给建议；
  - 不夸奖，不鼓励。
- **给事实，不给评价和建议。**
  - 数字、位置、状态，这些都可以给；
  - "需要加强节奏""建议慢速练习"，这些都不要。

## 3. 零冗余

- **默认状态不显示。** 原速、全曲、已同步、正常这类，不写；状态异常时才出现。
- **同一视口不重复同一信息。** 标题牌上有乐队名，封面下就不再写。
- **功能重复的控件要合并。** 比如"播放我的 / 播放原曲 / 对比播放"三个键，合成一个播放键加一个来源切换。
- **不加英文副标题**，比如"演奏报告 PERFORMANCE REPORT"。
- **不在标签上方再加一层小标签**（eyebrow）。

## 4. 提示与错误

- **Toast 不超过 6 个字。** 写"已复制"，不写"操作成功！已为您复制到剪贴板"。
- **错误要说清楚两件事：** 发生了什么，怎么解决。不道歉，不含糊。
- **空状态写一句话，再给一个动作。**

## 5. 数字与单位

- 单位小一号、浅一档，例如"0 ms"里的 ms。
- 数字用等宽字，位数固定。
- 能用图形表达的就不用文字。例如小节色格已经说明了哪里有问题，就不再写"第 12 小节有问题"。
