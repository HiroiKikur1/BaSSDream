# 过程：放开风格，收紧证据

## 1. 为什么同一个模型做视频好看、做应用难看

不是能力不同，是做事的条件不同。做视频（或海报、单张画面）的时候，下面这些条件几乎都成立；做应用的时候几乎都不成立：

| | 做视频 / 单张画面 | 做应用界面 |
|---|---|---|
| **眼睛** | 输出就是像素，每一版都渲染出来看，看了再改 | 写的是 XAML/组件代码，常常看不到结果（云端容器跑不了 WPF），写完就交 |
| **迭代** | 一个画面改十几轮 | 第一版能编译、功能对就算完成；第一版就是统计上最平均的样子，也就是“AI 味” |
| **注意力** | 全部花在好不好看上 | 大半花在数据、状态、bug、兼容现有代码上，好看是副产品 |
| **素材** | 有一首歌、一张封面、一段 MV，配色和母题直接从里面长出来 | 列表、按钮、设置项，没有天然素材，于是从“通用组件库”里取 |
| **媒介** | 自己挑最顺手的工具（HTML/CSS/SVG/Canvas/着色器），字体、混合模式、滤镜随手可用 | 被框架限制（WPF 的描边字、混合、字体回退都要绕），想到的效果写起来贵，于是退回能写的 |
| **约束的形状** | 给参考 + 放手 | 一长串“不要”。只有禁令没有参照时，最安全的做法就是什么都不做，结果是平庸 |

所以“偷懒”这个说法一半对：不是故意省力，而是**没有看见结果就停下了**。第一版永远平庸；好的画面都是看着结果改出来的。

## 2. 解决办法：两段式

约束越多越平庸，没有约束又会滑回默认答案。办法是**不约束风格，约束过程**：创作时放开，审查时收紧，两段分开做。

### 第一段：创作（放开）

- 只读：任务的事实、题材的世界、参考图、素材（曲绘、乐队官方素材）、本 skill 的“总纲”。**这一段不读反面目录和清单**，它们会让人缩手缩脚。
- **先把默认答案写下来，再绕开它。** 动手前用一两行写出“一个没想过的 AI 会怎么做这一屏”（例：白底、三张等圆角卡片、每张卡片上一行全大写小标签、柔和大阴影、Inter 字体）。这就是要避开的平均值。不是禁止，而是：如果最后的方案和它很像，要说得出为什么。
- **发散：至少三个空间逻辑不同的方向**，不是一个布局换三套配色。每个方向用一句话说“它在现实里是什么”（唱片内页、街机面板、排练室白板、谱册……）。
- **先给每个方向起名、写宣言，再画布局。** 名字一两个词（“谱册”“夕照电线”“排练室白板”），宣言四到六句，只写这个方向在空间、材质与颜色、尺度与节奏、构图、层级上的态度，不写具体布局。宣言让方向有立场，生成时才不会滑回平均值；也给自己留出诠释空间。（做法来自 canvas-design skill：先写一个“美学流派”的宣言，再把它画出来。）
- **隐性引用。** 题材（这首歌、这支乐队、贝斯）要织进形、色、构图里，懂的人一眼认出，不懂的人只看到一个好画面——像爵士乐手在即兴里引用别的曲子。直接摆一个贝斯剪贴画、拨片图标就是没织进去。
- **质量标尺写在前面。** 每个方向都按“顶尖团队花了几百小时手工做出来的”标准做：每处间距、对齐、颜色都是反复调过的。这句话不是客套，它决定停手的时机。
- **工具随便选。** 小样用 HTML/CSS/SVG/Canvas，甚至直接画 PNG，哪个顺手用哪个。字体库、混合模式、滤镜都可以用。小样是为了想清楚样子，不是产品代码。
- **每一版都渲染出来、自己看。** 不看图不算一版。

### 第二段：审查（收紧）

- 渲染真实尺寸 + 2 倍细节图（`tools/render.cjs`），读审计报告：实际画出来的字体、字号阶梯、圆角、阴影、框的数量。
- `tools/sheet.py --notan` 把参考和自己的方案拼在一张图上看。**数值和用户认可的参考比，不和绝对阈值比**：millsage 的歌词页亮部占 94%、几乎没有暗部，按“暗+中 ≥ 25%”的阈值会被判成“软”，但它不软——它的骨架是封面那一块满色中间调，加上一个深紫的大字焦点。阈值是起点，参考才是标准。
- **换一双眼睛**：把截图和参考交给 `design-critic` 子代理（它看不到你的思路，只看图），让它指出最像 AI 默认答案的地方。
- 过反面目录和清单。**每条命中要么改掉，要么写一句理由**。有理由的“违规”是设计决定；没理由的是默认值。
- 每一轮至少删掉一样东西。
- **精修轮：不加新东西。** 方向定了以后，想再加一个形状、一个效果、一个装饰时，先停下来问：怎样让已有的东西更成一体？把力气花在已有元素的间距、对齐、颜色关系、字距上。精修轮结束时检查：没有元素出界、没有意外的重叠、每样东西都有呼吸的空间。

### 第三段：交给用户

- 一张对比图（参考 + 2–3 个方向），一轮只问 2–4 个决定，让用户判活死。
- 用户否掉的写进项目的反面清单（原话照抄），认可的写进种子清单。下一轮从种子长出来。

### 第四段：翻译成产品代码

- 从批准的小样翻译到真实框架时最容易掉质量。翻译完必须用真实程序截图（WPF 用 `BassStation.exe --render-* out.png`），和小样用 `tools/overlay.py` 叠在一起比，差异列出来逐条处理或说明。
- 框架做不到的效果（比如某种混合模式），回到小样里找一个框架做得到的等价做法，而不是悄悄删掉。

## 3. 为什么这样能兼顾

- 风格上没有规定“必须什么样”，所以不会把所有画面压成同一种安全风格。
- 但“默认答案”需要三道关才能活下来：自己看图、数值和参考对比、陌生眼睛的批评。平庸的方案过不了这三道关，有意为之的大胆方案可以带着理由过关。
- 用户的判断沉淀成种子和反面清单，越用越准，而不是越用越多禁令。
